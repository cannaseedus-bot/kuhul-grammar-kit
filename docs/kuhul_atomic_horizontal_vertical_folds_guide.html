K-CUBE Geometry

The K-CUBE is a 6-face tensor where each face maps to a phase in the K'uhul fold cycle. Phases are arranged at equal angular intervals on the unit circle — i × π/3 radians — giving the geometry rotational symmetry and making the arc weight formula tractable.

Fold loop = micronaut memory cycle. Pop reads shared memory into Q. Xul writes the result back. The six phases are the full attention pass expressed as a closed geometric rotation — the cycle always returns to Pop.

Arc Weight Formula

Two numeric systems coexist in the K-CUBE and must not be confused:

  • Phase angles angles[i] = i × π/3 — fixed, structural, never trained. They define what each phase is.
  • Arc weights fold_arcs[6][6] — learned by the Adam optimizer. They define how strongly the output of phase i flows into phase j.
effective[i→j] = arc_w[i][j] × cos( angles[j] − angles[i] )

The cosine term multiplies the raw arc weight by the geometric cost of spanning a phase gap. A gap of 0 (same phase) gives cos(0) = 1.0 — the full weight survives. Larger gaps discount the weight, and opposing phases (gap = π) negate it.

ArcGap (Δ)cos(Δ)MultiplierMeaning
i → i  (same) 0 +1.00 × 1.0 No phase penalty — horizontal fold optimum
Pop → Wo π/3 +0.50 × 0.5 Adjacent — positive, half-strength
Pop → Yax 2π/3 −0.50 × −0.5 Two steps — opposing contribution
Pop → Sek π −1.00 × −1.0 Directly opposing — maximal cancellation
Pop → Ch'en 4π/3 −0.50 × −0.5 Two steps back — mirror of Pop→Yax
Pop → Xul 5π/3 +0.50 × 0.5 Adjacent wrap — same as Pop→Wo reversed
Key invariant: same-phase connections always have multiplier 1.0. Any horizontal fold — any connection between two nodes at the same phase — incurs zero geometric cost.

Vertical Folds

A vertical fold traverses the phase chain of a single node sequentially: Pop → Wo → Yax → Sek → Ch'en → Xul. It is the standard per-token attention pass — the node's full meaning emerges by going through each phase in order.

Characteristics

  • One node, six phases
  • Sequential — each step depends on the previous
  • Arc-weight cost accumulates at each phase hop
  • Full cycle: meaning built up in depth

When to use

  • Single-token resolution — what does this node mean?
  • KAST node compilation (KXC walks the phase chain)
  • Micronaut memory cycle (Pop=read SHM → Xul=write SHM)
  • Phase-chain kernels in .kuhul / .khl source
// Vertical fold — one node through all phases
node A {
  Pop:   q = read_shm(A)           // observe — Q-read
  Wo:    m = gate(q, weight)       // mask / weight
  Yax:   k = enumerate_keys(m)    // K-read
  Sek:   s = dot(q, k)            // QKᵀ score
  Ch'en: v = gather(s, values)    // V-gather
  Xul:   out = project(v)         // output → write SHM
}
// Arc costs: Pop→Wo ×0.5, Wo→Yax ×(−0.5), Yax→Sek ×(−1.0), ...

Each consecutive arc in the vertical chain applies the cosine multiplier for that gap. The full Pop→Xul traversal accumulates all six transitions. This is unavoidable for a single-node vertical pass — understanding the node's full meaning requires walking its depth.

Horizontal Folds

A horizontal fold connects two or more different nodes at the same phase level. Instead of descending through one node's phase chain, it operates across the width of a gram — relating multiple nodes at a chosen semantic depth.

Characteristics

  • Multiple nodes, one shared phase
  • Same-phase arc: multiplier always 1.0
  • No depth accumulation — relationship is captured at one level
  • Gram width = bigram (2), trigram (3), n-gram (n)

When to use

  • N-gram co-occurrence training over manifest nodes
  • Cross-domain grams spanning CSS + micronauts + words
  • Gravity-well routing: multiple micronauts evaluated at Pop simultaneously
  • @node cross-schema references — same-depth links
// Horizontal fold — two nodes at the SAME phase
// effective[0→0] = arc_w[0][0] × cos(0) = arc_w[0][0] × 1.0

bigram_at_pop(A, B) {
  q_A = A.Pop    // A's observation vector — pre-loaded
  q_B = B.Pop    // B's observation vector — pre-loaded
  return combine(q_A, q_B)   // relate at Pop — zero phase penalty
}

// Same logic at Sek for the computation relationship:
bigram_at_sek(A, B) {
  s_A = A.Sek    // A's QKᵀ vector
  s_B = B.Sek    // B's QKᵀ vector
  return combine(s_A, s_B)   // relate at Sek — zero phase penalty
}
Why horizontal folds are geometrically optimal: connecting A.Pop to B.Pop is a same-phase arc. The cosine penalty is cos(0) = 1.0. No arc-weight signal is discounted by phase geometry. The full trained weight flows between the nodes.

Vertical and horizontal folds are complementary, not competing. Vertical folds establish each node's individual meaning; horizontal folds capture how two fully-resolved meanings relate. You need both — but training the relationship between nodes benefits from horizontal, not vertical, geometry.

Manifest-Node Bigrams as Horizontal Folds

The manifest system makes horizontal folds the natural operation for n-gram training. The reason is that the manifest removes the vertical work from the bigram.

In a traditional language model, a bigram ["hello", "world"] is a co-occurrence of two surface strings. The model must learn what "hello" and "world" each mean by seeing them across many contexts — the vertical work (building per-token meaning) is entangled with the horizontal work (learning the relationship). Both happen simultaneously, in the same training gradient.

In the KHANARY manifest, every token is a manifest node with a full definition array pre-loaded at lookup time. The manifest has already done the vertical work:

// Manifest lookup at O(1) — no traversal
manifest["hello"]   → ["greeting", "intent:salutation", "⟁Pop"]
manifest["⟁CARD"]  → ["⟁BGpanel", "⟁BRlg", "padding:20px", "⟁BORDER"]
manifest["coordinator"] → ["eliza", "coder", "routing", "⟁Ch'en"]
Consequence: a manifest-node bigram is a pure horizontal fold. Both tokens arrive pre-defined — their full semantic content is already known. The model only trains the relationship between two already-understood objects at a chosen phase level. No vertical traversal is incurred during training.

And "pre-defined" means more than a dictionary entry. A manifest node is not a shorter label for a word — it is a handle into a semantic book:

// Traditional bigram token: "cause" → token ID 4312
// The ID says which word. Nothing more.

// Manifest-node: "cause" → ⟁CAUSE
// ⟁CAUSE is a book:
//   words:     why, because, cause, therefore
//   AIML:      causal patterns
//   ELIZA:     causal reflection operators
//   XCFE:      INFER · DECOMPOSE · COUNTEREXAMPLE
//   K'uhul:    fold:Sek
//   tracks:    causal-reasoning
//   relations: cause→effect · premise→consequence · evidence→conclusion

// The book doesn't have to be opened.
// XCFE requests only its operators.
// ELIZA requests only its patterns.
// K'uhul requests only the phase.
// A bigram of two books trains the relationship between two entire semantic domains.

A manifest-node bigram is therefore a co-occurrence of two books — or in graph terms, two neighborhoods. The manifest array is the adjacency list for each node: ⟁CAUSE's array declares its neighbors (word nodes, AIML nodes, XCFE nodes, K'uhul phase node, track nodes, relation nodes). A bigram of two manifest nodes is a same-depth traversal of two neighborhoods simultaneously. The horizontal fold captures the relationship between those two neighborhoods at a single phase level — with none of the vertical cost of building them from scratch in training.

// Surface bigram — vertical + horizontal entangled
bigram("hello", "world")
// model must learn: meaning of "hello" + meaning of "world" + their co-occurrence

// Manifest-node bigram — pure horizontal fold
bigram(manifest["hello"], manifest["world"])
// manifest["hello"] already fully resolved ← vertical done at manifest-build time
// manifest["world"] already fully resolved ← vertical done at manifest-build time
// model only trains: how these two semantic objects co-occur at phase Pop/Yax/Sek/...

This maps directly onto the arc weight formula at the same-phase point:

// Both tokens at Pop — observation relationship
effective[Pop→Pop] = arc_w[0][0] × cos(0°) = arc_w[0][0] × 1.0

// Both tokens at Sek — computation / dispatch relationship
effective[Sek→Sek] = arc_w[3][3] × cos(0°) = arc_w[3][3] × 1.0

The model trains the arc weight directly. Nothing is diluted by phase geometry. The bigram is horizontally optimal by construction.

Choosing which phase to run a horizontal fold at determines what aspect of the relationship the gram encodes. Each phase exposes a different semantic face of the node. The multiplier is always 1.0 regardless — phase selection is a semantic design choice, not a performance trade-off.

Opposing-Phase Arcs — Contrastive Folds

When two nodes in a gram sit at opposing phases (e.g. one at Pop, one at Sek), the formula gives:

effective[Pop→Sek] = arc_w[0][3] × cos(π) = arc_w[0][3] × (−1.0)

This is not a broken fold — it encodes a contrastive relationship. Pop (observation) and Sek (computation) are structurally opposed on the unit circle. A Pop→Sek arc means: the node's observation directly opposes its computation output. The negative multiplier subtracts rather than adds, which is the correct arithmetic for an antonym or inversion. Contrastive folds are valid; they just use the negation rather than the addition path.

Manifest Layout as Horizontal Organization

The flat key→array manifest structure is the data-layout counterpart of a horizontal fold. Every key sits at the same depth. There is no nesting to traverse. You address any node directly by name — O(1).

Nested schema — vertical access

{
  "ui": {
    "surface": {
      "card": {
        "panel": {
          "background": "..."
}

Getting "background" requires traversing 4 levels. Each level is a vertical step — equivalent to a phase hop with cost accumulation.

Manifest registry — horizontal access

{
  "⟁BGpanel": ["background:..."],
  "⟁PANEL":   ["⟁BGpanel", "padding:20px"],
  "⟁CARD":    ["⟁PANEL", "box-shadow:..."]
}

Getting ⟁CARD: one key lookup. Recursive expansion is done by the runtime — the schema stays flat. All keys at the same depth.

This is the drive-thru principle applied to data layout: pull up to the exact key, receive the array, drive away. No path to parse. No levels to descend. The manifest has pre-computed all vertical work into flat arrays — so query time is always a horizontal operation.

A manifest is independent of the runtime. The runtime mounts manifests — it does not generate or infer them. This is precisely why every key must be explicitly declared: the manifest is the authority on what a symbol means; the runtime is the authority on how to execute it. The two concerns are separated at the manifest boundary. A manifest declared once can be mounted into any conforming runtime — ASX browser engine, KXML inference graph, XCFE executor — without modification. Portability is a direct consequence of independence.

@node — Horizontal Links Across Schemas

The @node:Name syntax extends this to cross-schema references. When a schema key references another schema's node, it names it — not nests it:

// Both CardComponent and PanelBase are at the same registry depth
{
  "CardComponent":  ["@node:PanelBase", "elevation:2", "interactive:true"],
  "DashboardLayout":["@node:GridBase", "@node:CardComponent", "columns:3"]
}

@node:PanelBase does not copy or re-declare PanelBase. The registry resolves it on access. The reference is a horizontal link — two nodes at the same semantic depth, connected by name. This is the manifest-level encoding of a horizontal fold: a relationship at a shared registry layer, zero traversal depth.

@node and arc weights: a cross-schema @node reference is a same-depth connection. Both nodes exist at the key level of their respective registries. The effective arc weight is arc_w[i][i] × cos(0) = arc_w[i][i] × 1.0 — the horizontal fold optimum.

Primitive Edge Constraint — One Coordinate at a Time

A primitive runtime edge in Gruntime changes exactly one coordinate. This follows directly from the Cartesian product definition: adjacency in Gsemantic □ Gphase requires one factor to step and the other to stay fixed.

(v₀, Pop) ───────► (v₁, Pop)   horizontal — Δv, Δθ = 0
    │                  │
    │                  │         vertical — Δv = 0, Δθ = π/3

(v₀, Wo)  ───────► (v₁, Wo)

(v₀, Yax) ───────► (v₁, Yax)

A diagonal operation such as (v₀, Pop) → (v₁, Wo) is therefore not a primitive edge. It decomposes into a horizontal step followed by a vertical step (or vice versa), executed as an explicitly ordered two-step workflow. The decomposition order is architecturally meaningful — it determines which phase the semantic traversal happens in.

Gphase — The Immutable Six-Cycle

The phase factor Gphase is the directed six-cycle C₆:

G_phase = C₆:  Pop → Wo → Yax → Sek → Ch'en → Xul → Pop'

  with Pop' ≡ Pop (mod 2π)

This cycle is immutable — Gphase has a fixed topology. Only Gsemantic is declared by manifests and can be extended. The full runtime graph grows by expanding the semantic factor, never by changing the phase factor.

Runtime Position — Three Independent Coordinates

A runtime position in the system has three independent coordinates:

P = (v, k, θ)

  v  =  semantic position    — which node in the graph
  k  =  neighborhood depth   — how many hops from the origin
  θ  =  K'uhul phase         — which of the six fold phases (0, π/3, 2π/3, π, 4π/3, 5π/3)

These are genuinely independent. Graph distance k and phase offset Δθ are different structural coordinates — they must not be collapsed.

d(A, B) ≠ Δθ

Two nodes can be graph-adjacent (k = 1) while being at very different phases. Two nodes can be at the same phase (Δθ = 0) while being many hops apart in the graph. Phase similarity and graph proximity are orthogonal axes.

Horizontal Fold — Formal Definition

Horizontal fold:  (vᵢ, kᵢ, θ) → (vⱼ, kⱼ, θ)

  Δθ = 0   — no K'uhul phase transition occurs
  vᵢ ≠ vⱼ  — different semantic positions (two nodes)
  kᵢ, kⱼ   — depth may differ; phase governs, not depth

  Phase similarity:  Rθ = cos(Δθ) = cos(0) = 1.0
  Arc weight:        effective[i→i] = arc_w[i][i] × 1.0

A horizontal fold relates two nodes within the same phase. It is a traversal across the semantic graph at a fixed phase depth. Depth k can differ between the two nodes — what matters is that θ is shared. Graph distance does not determine phase cost.

Vertical Fold — Formal Definition

Vertical fold:  (v, k, θᵢ) → (v', k', θᵢ₊₁)

  Δθ = π/3   — one K'uhul phase step
  Standard transition: Pop → Wo → Yax → Sek → Ch'en → Xul

  Phase similarity:  Rθ = cos(π/3) = 0.5
  Arc weight:        effective[i→i+1] = arc_w[i][i+1] × 0.5

A vertical fold changes phase. It is a K'uhul state transition — not a graph traversal. The node may change (v → v') and depth may change (k → k'), but the defining property is the phase increment Δθ = π/3.

Cheat-Sheet

  • Vertical fold — one node, full Pop→Xul chain, meaning built in depth. Cost accumulates.
  • Horizontal fold — multiple nodes, one shared phase, relationship built in width. Always optimal (×1.0).
  • Manifest = horizontal — flat key→array, O(1) lookup, all keys same depth. The data structure is the geometry.
  • Manifest-node bigram = horizontal fold — vertical work done at manifest-build time; training captures only the relationship.
  • @node = horizontal link — same-depth cross-schema reference; no nesting, no traversal, full arc weight ×1.0.
  • @ prefix = directive — any JSON key or string starting with @ is an instruction to the runtime, not data. Uniform across manifests, XCFE, control programs, and SMCA metadata.
  • @kind / @ref — declare what a manifest key resolves into. "semantic" keys have fold-phase topology and can participate in phase-geometric horizontal folds; "atomic.css" keys do not.
  • @if / @then / @else — conditional fold branch inside a manifest array. Which phase path fires depends on the XCFE condition at runtime.
  • Phase selection is semantic — choose the phase that matches the kind of relationship you want to capture. All same-phase folds share the ×1.0 multiplier regardless of which phase.
  • Synonym collapse is free — surface variants resolve to the same manifest node; their bigrams merge without deduplication logic.
  • Symbol → book, not word → word — a manifest node is not a shorter label, it is a handle into an entire semantic book (words, patterns, operators, phase, tracks, relations). A bigram of two manifest nodes is a co-occurrence of two books. The manifest is an SCX semantic index; atomics matter because they decide which identities can stand for entire books before the system runs.

Book Coherence — Clustering Coefficient

Book size (|N(v)|) and Book coherence (κ(v)) are independent. A compact, high-κ Book is stronger semantic evidence than a large, low-κ Book.

κ(v)  =  2E_v / ( k_v × (k_v − 1) )

where  k_v  =  |N(v)|           (Book size — degree of v)
       E_v  =  edges among N(v)  (connections within the neighborhood)

κ(v) = 1   all neighbors mutually connected  →  tight Book, strong coherence
κ(v) = 0   no internal edges                →  star Book, low coherence

Equivalent triangle formulation: κ(v) = λ_G(v) / τ_G(v) where λ = closed triangles through v, τ = open triples centered on v. Triangle WHY ↔ REASON ↔ CAUSE is stronger evidence than star WHY ← CAUSE → REASON.

Notation lock: κi is structural clustering (graph-derived, deterministic). Ciearned is runtime confidence (accumulated from execution). Never conflate them. Ranking score: Si = Wi · Ciearned · Ri(Q, κi).

Helix Geometry

Without learning (ΔL = 0): the 2π phase cycle is a closed circle — 𝒦t+2π = 𝒦t. With learning (ΔL ≠ 0): the cycle does not close — 𝒦t+2π ≠ 𝒦t. The trajectory is a helix.

ΔL = 0:  𝒦_{t+2π}  =  𝒦_t       closed circle
ΔL ≠ 0:  𝒦_{t+2π}  ≠  𝒦_t       helix — Z offset grows with each cycle

Clean definition: "Learning changes the future semantic field produced by the same context."

Graph Query — Semantic Interrogation Layer

Semantic activation and semantic interrogation are distinct. FQ answers "which nodes are relevant?" — a subset. Query(F_Q, pattern) answers "what topology actually connects them?" — a structural read. The graph query layer sits between the activated field and Yax:

Graph Query Is a Deterministic Executor

The graph query layer is not a fourth embedding — it is a deterministic executor in the same category as XCFE. Structural, reproducible, O(graph-traversal).

graph.query    — Cypher-like pattern match within F_Q
graph.path     — reachability / shortest path between two nodes
graph.neighbor — Book(v) expansion at depth k
graph.arc      — ARC(X, Z, W, T, ΔH) property read on a named relationship
graph.pattern  — subgraph isomorphism: does F_Q contain this shape?

A Cypher-like match describes topology sought; the engine returns matching subgraphs from FQ:

-- what declared paths connect ORGANIC to LIFE within F_Q?
MATCH (organic)-[path*]->(life)
WHERE organic IN F_Q AND life IN F_Q
RETURN path

This maps directly onto ARC semantics: Cypher relationships are directed, named, and carry properties — the same structure as ARC(X, Z, W, T, ΔH):

(ORGANIC)-[:POSSIBLE_BIOSIGNATURE {weight:0.7, phase:Sek}]->(LIFE)

ARC( ORGANIC, LIFE, w=0.7, type=biosignature, ΔH=phase-offset )

Embedding similarity produces a flat set of relevant nodes. The graph query returns the declared semantic paths connecting them — the system is not relying exclusively on proximity in embedding space.

XCFE rules bind phases to execution stages. Each rule fires when its condition is satisfied. Rules that dispatch on phase state must carry an explicit phase gate — a derived-field condition alone can fire at any phase if that field is set.

Three correctness rules:
① Phase names are exact — "Ch'en" not "Chen". A misspelled phase value never matches.
② Phase-stage rules must carry a phase gate. Compound: {"op":"and","conditions":[phase==X, derived_field==value]}.

Hook abort = XCFE @else branch

An aborting hook on any pre-execution event is geometrically identical to an XCFE inline condition in a manifest array:

// XCFE in manifest — declarative
{ "@if":   "context.sandbox_level >= 2",
  "@then": ["⟁Sek", "route:execute"],
  "@else": ["⟁Wo",  "route:hold"] }

// Hook — imperative form of the same gate
micronaut.@register_hook("on_execute_before", (payload) -> {
  if (payload.context.sandbox_level < 2)
    return { abort: true, reason: "hold at Wo" }
})

Both produce the same G_runtime outcome: the vertical edge to Sek is not traversed; the micronaut remains at Wo. The hook form is used when the gate condition involves runtime state that cannot be declared statically in the manifest.

Hook chain as horizontal fold

Multiple handlers registered on the same event are evaluated sequentially at the same phase position — a horizontal fold across handler nodes:

  • All handlers share the same (v, θ) coordinate — Δθ = 0, arc cost 1.0
  • Each handler is a manifest node in the hook registry adjacency list
  • The first aborting handler collapses the fold early — subsequent nodes are not visited
  • Non-aborting handlers pass a mutated context forward — the output of each handler is the input neighborhood of the next

Hook contract rule H-6 and manifest independence

Rule H-6 states that hook arrays are declared in the manifest — the runtime can inspect them without instantiating the micronaut. This preserves the manifest independence principle: the hook registry is part of the declared neighborhood N(key), not a runtime side-effect. A consumer querying the manifest for "eliza" receives the capability array and the hook declarations as a single flat lookup — no instantiation, no graph traversal.

Six companion laws applied to hooks: Law 3 (manifest array = declared neighborhood) extends to hook arrays — each hook slot is a named entry in the micronaut's adjacency list, declaring which phase-gate observers are active before the fold runs. Law 6 (graph reachability does not grant execution authority) is exactly what the abort mechanism enforces: reaching a manifest node via graph traversal does not trigger the phase transition — the hook (the XCFE gate) must authorize it first.

init() / load_checkpoint() both at Pop — horizontal siblings

init() and load_checkpoint() are both at Pop (θ=0). They are horizontal siblings: same phase coordinate, different semantic roles. init() creates the tensor from scratch (no prior state); load_checkpoint() restores a prior Xul-committed state. Both are accessible by horizontal traversal from the Pop cluster. Their governs separation is contextual (no tensor governs arrays declared in this format), but the runtime routes between them by semantic query content — "create new" vs "restore from path."

save_checkpoint() at Xul — completing the Pop→Xul arc

save_checkpoint() at Xul (5π/3) and init() at Pop (0) form the outermost arc of the tensor's lifecycle: initialization at the cycle start, checkpoint at the cycle end. This is the K'ayab'→Kumk'u bookend pattern (gram checkpoint boundary) applied to a tensor object. The full phase path for a training step: Pop (init/load) → Sek (forward pass) → Ch'en (verify convergence / detect spike) → Xul (save checkpoint if authorized).

37 · Pipeline — C₆ Dataflow Folds

The .@.pipeline format maps the full C₆ cycle explicitly onto a stage graph. Each stage is a fold at its declared phase. The pipeline is the most direct expression of the product graph G_runtime = G_semantic □ G_phase seen in the format corpus: the stages are the semantic nodes (v_ingest, v_route, v_branch, v_fast_compute, v_compute, v_verify, v_emit); their @phase declarations are the phase coordinates.

Two Sek stages — why horizontal siblings don't collide

fast_compute and compute share phase θ=π but are at different semantic positions. In the product graph: (v_fast, Sek) and (v_expert, Sek) are distinct nodes — same phase coordinate, different semantic axis. The route stage at Wo selects one by advancing along a horizontal arc to either v_fast or (via branch) v_expert. This is not a governs-intersection collision because both are pipeline stages, not micronaut folds — the routing is explicit XCFE (@if/@then/@else), not pattern-match based.

The verify→route retry arc — backward vertical hop

The retry path from verify (Ch'en, θ=4π/3) back to route (Wo, θ=π/3) is a backward edge in phase space:

Δθ = π/3 − 4π/3 = −π  (backward half-cycle)

Arc cost = arc_w × cos(−π) = arc_w × (−1). This is the same opposing-phase cost as the ELIZA-1 Pop→Sek operator pair — a negative arc encoding an inversion. Here the inversion is: Ch'en determined the output is insufficient → re-enter the plan phase (Wo) to try a different route. The pipeline does not advance to Xul with a failing result. The negative arc is the cost of quality enforcement.

Simple-path skip: Wo→Sek over Yax

When route_decision is "simple", the pipeline jumps from route (Wo, π/3) directly to fast_compute (Sek, π), skipping branch (Yax, 2π/3). The arc Wo→Sek = Δθ = 2π/3, cost = cos(2π/3) = −0.5. The simple path incurs a −0.5 arc where the expert path gets +0.5 (Wo→Yax) + (−0.5) (Yax→Sek). Both paths carry the same aggregate Wo-to-Sek cost (−0.5 one-hop vs +0.5 then −0.5 = 0 net), but the expert path expands through Yax first, which provides semantic qualification that the simple path skips.

@parallel at Yax — fold fan-out vs fold selection

Standard governs-intersection routing at Yax selects the single best-matching fold. The pipeline's @parallel block at the branch stage instead fan-outs to two simultaneous folds (expert_a and expert_b). Both folds are at (v_expert_a, Yax) and (v_expert_b, Yax) — same phase, adjacent semantic positions. The parallel execution is a horizontal fan-out rather than a horizontal selection: both are traversed simultaneously, their outputs merged at the compute stage. This is the only documented case in the format corpus where a Yax-phase node activates multiple successors rather than one.

39 · π Token Base · Brain Fleet · Atomic Block Law

π geodesic as a fixed phase sequence

The π token base introduces a fold sequence that is neither horizontal nor vertical in the K'uhul sense — it is deterministic transcendental. Each π digit d_n produces a rotation of Δθ = (2π/10) × d_n. The cumulative sequence θ_n = θ_{n-1} + (2π/10)×d_n mod 2π traces a path through the phase circle that is fixed, not learned, and not tunable.

In G_phase = C₆ terms: the standard K'uhul phase cycle advances in steps of π/3 (one sixth of the circle). The π rotation steps are (2π/10)×d_n — irrational multiples of π/3 for most digits. This means the π-driven path does not align with the C₆ phase grid; it traces a denser spiral through the phase space that intersects the six C₆ nodes non-periodically. The π sequence is therefore a supplementary phase structure — it operates on the continuous rotation manifold, while the C₆ cycle operates on the discrete six-point graph.

Deep Thinking Index — product-graph depth formula

D = N × G × T × Σ(κ_i) is a product-graph depth metric. In fold-theoretic terms: N=8 is the chain length (horizontal distance across the brain fleet); G=4 is the SIMD width (parallel horizontal fan at each node); T=8 is the tensor rank (depth of the product space at each position); κ_i ≈ 1.0 is the per-brain curvature (deviation from flat — a flat manifold has κ=1.0). D = 2048 is the effective semantic volume that the 8-brain chain can hold in one forward pass — not traversal depth alone, but the full product of chain length × fan-width × rank × curvature.

Brain fleet — horizontal 8-node semantic chain

B1→B2→…→B8 is a horizontal chain in G_semantic: each brain is a specialized semantic node, and the chain advances from routing (B1) through domain experts (B2–B7) to synthesis (B8). In K'uhul phase terms, each brain in the chain operates at whatever phase its task requires — B2 (PROOF_ENGINE) likely lives at Sek+Ch'en (execute + verify); B1 (MASTER_ROUTER) at Pop+Wo (perceive + plan). The chain is a horizontal structure; the phase assignment within each brain is vertical. The 8D tensor shape [8,8,8,8,8,8,8,8] encodes one axis per brain — the product of all 8 axes is the full fleet state tensor.

Atomic Block Law — Ch'en as the update boundary

The learning rule fires at Ch'en (θ=4π/3): A += δA per Ch'en phase. This is the same boundary as the confidence.json update path (§36) and the self-aware tensor's convergence monitor (§40). Ch'en is the canonical update phase across all three learning mechanisms in the stack:

The atomic block law operates at a lower authority level — it is the per-cycle fine-grained routing update, not the long-term capability update. Law 5 (vertical fold = Δθ=π/3, XCFE-authorized) applies only to the confidence/checkpoint paths; atomic block updates at Ch'en are within the authorized Ch'en scope.
